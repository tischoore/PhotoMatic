# PhotoMatic

A native Windows desktop application written in Rust, using [native-windows-gui](https://github.com/gabdube/native-windows-gui) for a classic Win32 look: a real menu bar, native dialogs, and no browser/canvas rendering underneath and has no dependancies on online resources while running. It is also using multiple worker threads to do the actual work concurrently.

## Features

- **Windowed or full-screen** startup mode, based on a saved user preference.
- **Three-region layout** — a full-width Project Information strip (300px tall) across the top, with a Left Navigation panel (1/5 width) and Context Window (4/5 width) filling the rest. Project Information and Left Navigation use a darker gray background; the Context Window is lighter.
- **Source Directory** — an editable text box plus a `Browse...` folder picker, aligned to the top-left of the Project Information strip. The chosen (or typed) folder is stored in the project file and restored whenever a project is loaded.
- **File Types** — checkboxes for `*.jpg`, `*.CR2`, and `*.gif`, directly below Source Directory, controlling which file extensions are included from that folder. All are checked by default; the selection is stored in the project file and restored whenever a project is loaded.
- **Link RAW and compressed images** — a checkbox next to File Types, unchecked by default and stored in the project file. When checked, every Scan Directory run (and once immediately when the checkbox is checked for an already-scanned project) pairs each `.CR2` file with its compressed sibling — same directory, same filename stem, case-insensitive, strictly one-to-one — and stores a bidirectional link between the two `images` rows; an ambiguous group (e.g. two candidates sharing a stem) is left unlinked rather than guessed at. A linked RAW image is excluded from Generate Events clustering, so only its compressed sibling forms or joins an event, and is also removed from every collection it belongs to (default or user-created) — its compressed twin already represents it there. Unchecking the option clears every existing link immediately, makes previously-linked RAW photos independently event-eligible again on the next Generate Events run, and restores every image, RAW included, to the default collection. Both the linking and the collection membership are kept unconditionally in sync with the checkbox on every Scan Directory run and every Generate/Update MetaData run, not just the checkbox click, so the database never drifts from the current setting regardless of history.
- **Scan Directory** — a button pinned to the bottom-right of the Project Information strip. Recursively walks the Source Directory on a background thread (so the rest of the GUI stays responsive), counting files matching the enabled File Types. While scanning, the button is disabled and a marquee progress bar above it is shown.
- **Generate MetaData** — a button next to Scan Directory, disabled until a scan has populated the database. Reads each scanned image's EXIF data (date taken, width, height, exposure time, ISO, focal length, GPS coordinates and altitude) on a small pool of background reader threads and writes it to the corresponding `images` row, so a later cataloguing/browsing UI has it available without re-reading files from disk. Only images that haven't been processed yet are read, so re-running it after adding more images (via another Scan Directory) only picks up the new ones; a rescan never wipes previously generated metadata. Every run also ensures the project's default collection exists — named after the project file, described as "Default collection containing all images within the project" — and links every current image into it, idempotently, so a rescan's new images get linked too. The button itself reads **Generate MetaData** until that first happens, then **Update MetaData** thereafter, with the label derived from whether the default collection already exists rather than a separate stored flag.
- **Event Gaps / Event Distance / Generate Events** — three small numeric inputs (Event Gaps: burst seconds, session minutes, multi-hour hours; default 10/60/8), two more (Event Distance: session km, multi-hour km; default 2/50), plus a **Generate Events** button next to Generate MetaData, enabled under the same condition. Clusters every image in the project by `corrected_date_taken` at three nested granularities — **Tight Burst**, **Session**, **Multi-hour** — by sorting photos chronologically and starting a new group wherever the gap since the previous photo exceeds that tier's threshold. For Session and Multi-hour, a group also splits wherever the GPS distance since the previous photo exceeds that tier's Event Distance value, when both photos have GPS coordinates (a photo missing GPS simply falls back to the time-gap-only behavior for that pair); Tight Burst has no distance check, since GPS noise isn't a meaningful signal at that time scale. A photo can belong to up to three groups at once (its burst, its session, and its multi-hour block). Only groups of 2 or more photos become an event; a photo with no neighbor within a tier's threshold simply has no event for that tier. Each new event's title defaults to its photo count. Every run clears and fully rebuilds the results (unlike Generate MetaData's incremental behavior), and runs synchronously since it only touches already-cached data — since a rebuild would silently erase any title/notes already typed into an event (see Event tabs below), Generate Events first shows a Yes/No confirmation whenever at least one event currently holds a non-default title or non-empty notes, and does nothing if answered No. The Event Gaps and Event Distance values are stored in the project file and restored whenever a project is loaded.
- **Set Time Correction** — a button next to Generate Events, for aligning clock drift between different cameras' photos. Since it decodes a thumbnail for *every* event-eligible photo in the project up front, clicking it first opens a small "Generating Thumbnails" spinner dialog (with its own **Cancel** button) while that happens on a background thread, so the app gives immediate feedback instead of appearing to do nothing for however long the project's full photo count takes to decode; Cancel (or the spinner's own close button) stops generation and closes without opening the dialog, the same as Cancel elsewhere in this flow. Once decoding finishes, the spinner is replaced by the real dialog: one card ("lane") per top-level directory that holds at least one event-eligible photo (a linked RAW is skipped in favor of its compressed sibling, same rule Generate Events uses; images sitting directly in the Source Directory get their own "(root)" card), ordered by photo count descending (the directories most likely to serve as a useful alignment reference come first) and laid out as a wrapping grid, two cards per row, so the dialog reads as a compact matrix rather than one ever-taller list; a vertical scrollbar appears alongside the grid whenever it doesn't fit the window. Each card is headed by its directory name in bold, slightly-larger text alongside its live offset from the baseline lane — `0` for the lane with the most photos, a signed `HH:MM:SS` for every other lane (or "no date yet" if its selected photo hasn't had Generate MetaData run on it) — recalculated and redrawn on every thumbnail click, including a click in the baseline lane itself, since that shifts every other lane's offset too. Each card also shows *every* photo in that directory as a small clickable thumbnail in its own horizontally-scrollable strip (a scrollbar appears under a card's strip only if it has more photos than fit at once) — clicking a thumbnail selects it, marked with a visible border, replacing the older Prev/Next-per-lane design entirely. Clicking a lane's *already-selected* thumbnail a second time deselects it instead, hiding the border on every thumbnail in that lane and excluding the whole directory from the correction: its header shows "not selected" in place of an offset, and Accept leaves its photos' `corrected_date_taken` untouched. Clicking any thumbnail in a deselected lane re-selects it, restoring the lane to the correction and its header to a normal offset. Click each remaining card's thumbnail for the photo showing the same real-world moment (e.g. a synchronized clock, or the same visible event, across cameras), then **Accept**: the included lane with the most photos becomes a fixed baseline, and every other included lane's `corrected_date_taken` is shifted, in one atomic transaction, by the difference between the baseline's and that lane's currently-selected photo — applied to every image row under that directory, RAW included even when hidden behind its compressed sibling; the baseline itself, and any deselected lane, is left unchanged. **Cancel** (or the dialog's own close button) discards every selection. Accept requires at least two lanes to be included, and Generate MetaData already having run on both the baseline's and every other included lane's currently-selected photo — otherwise it shows an error and the dialog stays open. Since `corrected_date_taken` drives ordering and Generate Events clustering everywhere else, Accept also re-runs Generate Events immediately afterward (with the same edited-events confirmation Generate Events itself shows), so the app is never left showing events clustered on stale timestamps.
- **Project database** — alongside the JSON project file, a SQLite database (`<name>.sqlite3` next to `<name>.json`) is created on first save and migrated forward automatically every time it's opened. A Scan Directory run writes to it incrementally as the scan progresses (one top-level directory, or the batch of files sitting directly in the Source Directory, at a time) rather than only once the whole tree has been walked. The `directories` table holds only top-level directories (one level below the Source Directory); each `images` row is keyed by a stable hash of its path, carries a foreign key to the top-level directory it lives under (`NULL` for images placed directly in the Source Directory), and (once Generate MetaData has run) its EXIF-derived date taken/width/height/exposure time/ISO/focal length/GPS latitude/longitude/altitude, plus a `corrected_date_taken` column seeded to the same value at that same moment — every ordering, Generate Events clustering, and displayed "Date taken" elsewhere in the app reads `corrected_date_taken` rather than the original EXIF `date_taken`, which stays independently correctable via Set Time Correction (see above), and resettable back to it either one photo at a time via the Image Viewer's Clear Time Correction or for every image at once via the Edit menu's Clear All Time Correction (see below), without ever losing the original — plus a self-referential `linked_key` column pointing at its RAW/compressed sibling's row, written by Link RAW and compressed images (see above), `NULL` when unlinked, a `rotation` column (degrees clockwise, `NULL` meaning unrotated) written by the Image Viewer's Rotate button (see above), and seven `color_black_r`/`color_black_g`/`color_black_b`/`color_white_r`/`color_white_g`/`color_white_b`/`color_blend` columns (the first six 0-255, `color_blend` a 0.0-1.0 fraction, `NULL` under the same all-or-nothing rule meaning never auto-corrected) written by the Image Viewer's Auto Correct button and Blend slider (see below). Rescanning never duplicates existing rows or overwrites any per-directory or per-image metadata a later editing UI adds. Generate Events populates two more tables: `events` (one row per detected group, with its tier, a user-editable `title` defaulting to the photo count, and a user-editable `notes` column) and `event_images`, a join table linking each event to its photos. Generate/Update MetaData populates `collections` (a named, described group of images, each with a unique single-character `shortcut`, plus a `current_img` column — the key of the photo the Image Viewer should resume on, `NULL` for its first photo or before any photo's been viewed, see **Image Viewer — resume position** below) and `collection_images`, its join table linking a collection to its member images — one `collections` row is the project's default collection (created automatically, `shortcut` `"d"`), and the user can create further ones via **Add Collection...** (see below).
- **Left Navigation directory tree** — filling the entire Left Navigation panel, a tree view lists every top-level directory from the project database, each expandable into an `ext (n)` child item for every currently-enabled File Type showing that directory's image count (0 when present but empty). A File Type unchecked in the Project Information strip has no child item at all, even if the database still holds images of that type from an earlier scan. It's read entirely from the database and the File Types selection, and rebuilt whenever either changes: when a project with an existing database finishes loading, after every Scan Directory run, after every Generate Events run, and immediately on every File Types checkbox toggle. Right-clicking a directory node or one of its File Type children (`ext (n)`) shows a three-item context menu: **Open in Explorer** (opens that directory in Windows Explorer), **Image List** (opens/switches to a Context Window tab for it — see below), and **View Images** (opens the Image Viewer directly for that directory/type's photos, starting at the first one, ordered chronologically by `corrected_date_taken` (falling back to path when dates tie or are still unset) — same photo list and order as its Image List tab).
- **Left Navigation Events node** — an `Events` node always sits at the bottom of the tree, below every directory, regardless of directory names. Once Generate Events has produced at least one event, it expands into one child per event type that actually has events (`Tight Burst`/`Session`/`Multi-hour`, each labeled with its count, e.g. `Session (4)`), collapsed by default since a type can hold many events; each type node expands into its events, labeled with their (possibly user-edited) title, in chronological order. Clicking an event opens (or switches to) its Context Window tab — see Event tabs below — and selects that event's node, so the tree always shows which event is currently displayed, including when Prev/Next or a tab-strip click changes it.
- **Left Navigation Collections node** — a `Collections` node always sits at the bottom of the tree, below Events. It expands into one child per collection, labeled with its name, ordered by id ascending (so the default collection, always the lowest id, lists first). Right-clicking a collection shows a four-item context menu: **Edit** (reopens the Add/Edit Collection dialog, prefilled, to change its title/notes/shortcut), **View** (opens the Image Viewer for the collection's photos, ordered by date taken, resuming on whichever photo was last viewed — disabled while the collection has no photos yet), **Delete** (asks for confirmation, then removes the collection and its `collection_images` rows and refreshes the tree; disabled for the default collection, since deleting it would silently hand "default" status to a different collection on the next Generate/Update MetaData run), and **Export...** (see below) — the last two are also disabled while the collection has no photos yet.
- **Export collection** — the Collections node context menu's **Export...** item opens an **Export** dialog: a **Recompression** choice (**None**/**Large**/**Small**), a **Rescale** checkbox with **Width**/**Height** fields (enabled only once Large or Small is chosen; checking it reveals the fields, along with a hint that either can be left blank), and an output directory text box plus a folder-picker **Browse...** button. Pressing **Export** warns (Yes/No, continuing either way) if the chosen directory isn't empty, then closes this dialog and opens an **Exporting** dialog — just a spinner and an **Abort** button — while a background thread copies the collection's photos, in the same date-taken order used everywhere else. Each output file keeps its original name prefixed with a zero-padded index (e.g. `001_`, digit count matching the collection's photo count); with Recompression **None** it's copied byte-for-byte; with **Large**/**Small** it's re-encoded as a `.jpg` at 80%/50% JPEG quality, and always has its stored rotation and color correction (see **Image Viewer — Auto Correct**, below) baked into the output pixels, since neither is ever written into the original file. Rescaling always preserves the photo's aspect ratio: with only Width or only Height given, the other dimension is derived to match; with both given, whichever one is numerically closer to the photo's own size (the smaller pixel change) drives the scale, so the result never overshoots either request more than necessary — and for a 90°/270°-rotated photo, Width/Height describe the final, right-side-up output (see Image Viewer — Rotate, above), not the file's stored orientation. Abort stops after the file currently being written finishes (never a partial file); the Exporting dialog closes itself once the run stops, reporting a summary only if it was aborted or any individual photo failed — a fully clean export stays silent.
- **Context Window tabs — Image List** — choosing **Image List** from the Left Navigation tree's context menu opens a tab in the Context Window, or switches to it if already open. The tab is named after the directory (e.g. `50D`) or, for a File Type child, `directory/type` (e.g. `50D/jpg`). Its content is a table of that directory's images from the database — Path, Date taken, Corrected date taken, Width, Height, Focal length, ISO, Exposure time, Location, Altitude — with a native vertical scrollbar. Date taken is the original EXIF value; Corrected date taken is the (initially identical) value everything else in the app — ordering, Generate Events, this table's own sort order — actually uses, and is shown alongside it so the two can be compared. Tabs are native Win32 tabs with no per-tab close "x"; close the active tab with Ctrl+W, or right-click any tab's header for a one-item context menu, **Close Tab**, which closes that tab whether or not it's the active one.
- **Context Window tabs — Event tabs** — clicking an event in the Left Navigation tree's Events node opens (or switches to) its own tab, titled `Event #<id>` (a stable identifier — the tab's header itself is never renamed, since native-windows-gui can't safely rename a tab's header after creation). In the top-left, a **Title** label and input box hold the event's title (defaulting to its photo count), edited freely; below that, a **Notes** label and a multi-line text box hold a short free-text description. Both save to the database on every keystroke, and an edited title updates the tree's label for that event immediately. In the top-right, a **View Images** button and **Prev**/**Next** buttons — the latter step to the previous/next event within the same type, looping past either end; the rest of the tab is a photo table for the event, in the same Path/Date taken/Corrected date taken/.../Altitude shape as an Image List tab's. Closing works the same as an Image List tab (Ctrl+W or right-click **Close Tab**).
- **Image Viewer** — opened from an event's photo table via either its **View Images** button or, in the Left Navigation tree, right-clicking the event itself and choosing **View Images** from its context menu (starting at the first photo either way); also opened from the Left Navigation tree's Collections node via a collection's **View** context menu item (photos ordered by date taken, resuming where that collection was last left off — see **Image Viewer — resume position**, below), or from a directory node (or one of its File Type children) via its own **View Images** context menu item, starting at its first photo in the same order as its Image List tab. Runs in its own non-modal window, on its own thread (native-windows-gui allows only one message loop per thread, the same reason the Settings dialog does), titled after the event's title as of the moment the window opened — never re-synced if the title is edited afterwards. Along the top, a status label (the current photo's path and its position, e.g. `3 of 12`) plus **Prev**/**Next** buttons fill most of the window with the current photo, scaled to fit while preserving its aspect ratio and rotated per its saved rotation (see **Rotate**, below); unlike an event tab's Prev/Next, there's no wraparound — Prev is disabled on the first photo, Next on the last — and the Left/Right arrow keys do the same thing. A photo in a format Windows' built-in codecs can't decode (e.g. `.CR2`/RAW) shows "preview unavailable" in the status label instead of an image, but still supports Prev/Next and Meta Data. When the current photo has a linked RAW/compressed counterpart (see Link RAW and compressed images, above), a **Toggle RAW** button (Alt+W) next to Prev/Next switches the view between the two — re-decoding, re-fitting, and updating the status label and Meta Data dialog for the counterpart's own record; Prev/Next always reset back to the compressed side. Below the top row, one toggle button per collection in the project, labeled with that collection's name and shortcut (e.g. `Landscape (L)`) — pressed when the current photo belongs to that collection, unpressed otherwise; clicking it, or pressing its shortcut key (no Ctrl held) anywhere in the window, adds or removes the photo from the collection immediately (writing straight to the `collection_images` table) and updates every collection button's state as Prev/Next/Toggle RAW change which photo is current. Its own menu bar: **File** > Close (Ctrl+W), **Edit** > Meta Data... (a modal dialog listing every database field for the current photo) and Clear Time Correction (see below), **Help** > About. A **Delete** button next to Toggle RAW, also reachable via the Delete key anywhere in the window, asks for confirmation, then removes the current photo — and its linked RAW/compressed counterpart, if any — from every collection (default included) and every event; the image file and its `images` row are left untouched, so it reappears after a later Generate/Update MetaData and Generate Events run. Browsing then continues on the next remaining photo (or the previous one, if the last photo was deleted), closing the window if none remain.
- **Image Viewer — Image Nr** — an **Image Nr:** label and input box next to Prev/Next holding the current photo's 1-based position (e.g. `12`); typing a number and pressing Enter jumps straight to that photo (resetting Toggle RAW back to the native side, same as Prev/Next) if it's between 1 and the photo count, the quickest way to reach the start or end of a long list without holding Prev/Next. An out-of-range or non-numeric entry is rejected and the box snaps back to the current photo's actual number instead. Left/Right, Delete, and every collection's shortcut key are suppressed while this box has keyboard focus, so typing in it never navigates, deletes the photo, or toggles a collection by accident.
- **Image Viewer — Rotate** — a **Rotate** button (Alt+R) next to Delete rotates the current photo (or its RAW/compressed counterpart, if Toggle RAW is active) 90° clockwise, wrapping from 270° back to 0°, and writes the new value straight to the `images.rotation` column so it's remembered across Prev/Next, closing and reopening the viewer, and future sessions. The displayed bitmap is re-decoded and re-fit rotated on every redraw, including prefetched neighbors.
- **Image Viewer — Auto Correct** — a push-button-style toggle (a checkbox rendered with Win32's `BS_PUSHLIKE` style, so it stays visually depressed while on, next to Rotate) for a brightness/contrast correction on the current photo (or its RAW/compressed counterpart, if Toggle RAW is active), using Simplest Color Balance (Limare, Lisani, Morel, Petro, Sbert — IPOL 2011): the darkest and brightest 1% of each RGB channel's pixel values are clipped, and the rest linearly stretched to the full 0-255 range. Checking it computes the correction once, on a background thread, from a full-resolution decode of the source file (not the on-screen preview, so the result doesn't depend on window size) — it disables itself meanwhile and re-enables once done, staying depressed on success or releasing again if the computation fails — and stores it as six small numbers (a low/high clip point per channel) in the `images` row, the same non-destructive "viewing parameter" approach Rotate uses: the source file on disk is never modified, and the correction is only ever applied when rendering a bitmap for display or for a recompressed export (see **Export collection**, above), never baked in until then. Unchecking it deletes those six stored values (plus the Blend value below) immediately (synchronously — no decode needed) and the photo reverts to its uncorrected pixels right away; navigating to a different photo, or toggling Toggle RAW, always shows that photo's own current state, whether checked, unchecked, or (briefly, disabled) still computing.
- **Image Viewer — Blend** — a slider (a native trackbar) next to Auto Correct scaling how strongly the computed correction above is applied to the current photo (or its RAW/compressed counterpart, if Toggle RAW is active), from 0% (the photo's original, uncorrected pixels) to 100% (the full computed stretch), stored in the `images` row's `color_blend` column and, like Rotate and Auto Correct itself, only ever applied when rendering a bitmap for display or export, never baked into the source file. Enabled and set to the photo's own stored value only while it has an active correction; disabled and shown at 50% otherwise — the same 50% a *freshly checked* Auto Correct starts at, since a brand-new correction defaults to a half-strength blend rather than full strength. Moving it is instant: unlike checking Auto Correct itself, no re-decode or histogram recomputation is needed, just a re-blend of the already-computed clip points, so the preview updates live as the slider is dragged. The chosen blend is remembered across Prev/Next, Toggle RAW, and closing/reopening the viewer, and is baked into a recompressed export's output pixels exactly like rotation and the correction itself (see **Export collection**, above) — a photo exported at, say, a 25% blend looks 25%-corrected in the exported file, not fully corrected. Auto Correct predating this feature (already carrying stored clip points from before the Blend slider existed) is treated as if it had always been at 100%, so no existing correction's appearance changes.
- **Image Viewer — Clear Time Correction** — an Edit menu item (mnemonic only; no Windows-standard accelerator exists for this action) that resets the currently displayed photo's (or its RAW/compressed counterpart's, if Toggle RAW is active) `corrected_date_taken` back to its original `date_taken`, undoing any shift a Set Time Correction run (see above) applied to it. Takes effect immediately, with no confirmation.
- **Image Viewer — resume position** — opening the Image Viewer from a collection's **View** context menu item starts it on whichever photo was last displayed in that collection, rather than always the first one. Every time a photo is shown (initial open, Prev/Next, or the redisplay after a Delete), its key is written to that collection's `collections.current_img` column — except when it's the collection's first photo, which stores `NULL` instead, since "start at the first photo" is already the default for an empty/unset column. If the stored photo was since removed from the collection (e.g. via Delete), the viewer falls back to the first photo instead. This only applies to a collection opened from the Collections node — the Image Viewer opened for an event or a directory always starts at the first photo, as before.
- **Image Viewer prefetching** — as soon as a photo is shown, its two next neighbors and its previous one are decoded and fit to the window on background threads, and the last 5 decoded photos are kept in memory; a Prev/Next that lands on an already-prefetched neighbor displays it instantly instead of blocking on disk I/O and image decode. Resizing the window invalidates every cached/in-flight bitmap (they were fit to the old size) and starts fresh at the new one.
- **File menu** — `New` (Ctrl+N) resets the current project; `Open...` (Ctrl+O) loads a project from disk; `Save` (Ctrl+S) and `Save As...` (Ctrl+Shift+S) write it back; `Exit` (Alt+F4) closes the application.
- **Edit menu** — `Settings...` opens a dialog to switch between Windowed and Full screen, with Accept/Cancel. Accept saves the choice to disk and applies it immediately; Cancel discards the change. `Add Collection...` opens a dialog with Title, Notes, and Shortcut key fields (plus Accept/Cancel); Accept validates the title is non-empty and the shortcut is exactly one character not already used by another collection (showing an error and leaving the dialog open otherwise), then creates a new row in the `collections` table and refreshes the Left Navigation tree's Collections node. `Clear All Time Correction` asks for confirmation (Yes/No, since it can't be undone short of re-running Set Time Correction for every directory again), then resets `corrected_date_taken` back to `date_taken` for every image in the project at once — the whole-project counterpart to the Image Viewer's per-photo Clear Time Correction (see below) — and re-runs Generate Events afterward, same as Set Time Correction's own Accept.
- **Help menu** — `About` shows the application name, author, and year.
- **Keyboard shortcuts** — every menu has an Alt-mnemonic access key (e.g. Alt+F for File), and the standard Windows accelerators above are wired for real, not just labeled.
- **Persisted settings** — stored at `%APPDATA%\Tischer\PhotoMatic\config.toml`.

## Prerequisites

- **Rust** (stable, MSVC toolchain) — install via [rustup](https://rustup.rs). The pinned toolchain is in `rust-toolchain.toml`, so `rustup` will fetch it automatically on first build.
- **MSVC linker** — install the "Desktop development with C++" workload from [Visual Studio Build Tools](https://visualstudio.microsoft.com/downloads/#build-tools-for-visual-studio). Without this, the build fails with `linker 'link.exe' not found`.
- **SQLite** — statically bundled into the executable via `rusqlite`'s `bundled` feature, so there's nothing separate to install. The first build compiles SQLite from source using the same MSVC toolchain, so expect a slower first build.

## Build and run

From a terminal, in the project root:

```powershell
cargo build          # compile
cargo run             # compile (if needed) and launch target\debug\photomatic.exe
cargo build --release # optimized build, output in target\release\photomatic.exe
```

### From VS Code

Open this folder in VS Code and press **F5** to build and launch under the debugger. This requires the [CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb) extension (VS Code will prompt to install it if missing). Use `Ctrl+Shift+B` to just build without debugging.

### Continuous integration and releases

`.github/workflows/ci.yml` builds and runs `cargo test` on `windows-latest` for every push and pull request. `.github/workflows/release.yml` triggers on pushing a tag matching `v*` (e.g. `v1.0.0`): it builds `cargo build --release`, zips `photomatic.exe`, and publishes it to the repo's GitHub Releases page automatically — no separate portal setup is needed, since both workflows are defined entirely by these committed YAML files.

## Testing

```powershell
cargo test
```

See `CLAUDE.md` for this project's testing convention (every feature must ship with its own independent test).
